# Основа мода

Работаем по принятому порядку: сначала рабочие основы, затем расширение и полировка.
Демонстрационный контент использует ванильные текстуры; это примеры подключения систем.

## Каталог контента

`src/main/content/tech-mod.content.json` — основной каталог. Добавьте запись в нужный массив,
запустите `gradlew.bat build`. Задача `generateContent` создаёт модели, blockstates, переводы,
добычу, теги и worldgen в `build/generated/tech-content`. Эти файлы включаются в JAR.
Каталог также читается модом при старте для регистрации объектов. Перезапустите игру после изменений.
Сгенерированные файлы не редактируйте: меняйте каталог или генератор `gradle/content.gradle`.

### Обычные блоки

```json
{"name":"steel_block", "display":"Steel Block", "display_ru":"Стальной блок",
 "texture":"tech_mod:block/steel_block", "hardness":5,
 "tags":["tech_mod:machine_casings"], "tool_tag":"minecraft:needs_iron_tool"}
```

Добавьте в `blocks`; текстуру положите в `src/main/resources/assets/tech_mod/textures/block/steel_block.png`.
Для регистрации из Java: `ModBlocks.register(name, properties)` либо перегрузка с фабрикой своего Block.
Java-регистрация сама не создаёт ресурсы; каталог обеспечивает и регистрацию, и ресурсы.

### Руды

```json
{"name":"tin", "display":"Tin Ore", "display_ru":"Оловянная руда",
 "texture":"tech_mod:block/tin_ore", "deepslate_texture":"tech_mod:block/deepslate_tin_ore",
 "hardness":3, "vein_size":8, "veins_per_chunk":10, "min_y":-32, "max_y":96,
 "biomes":"overworld", "drop":"minecraft:raw_iron"}
```

Добавьте в `ores`. Автоматически создаются `tin_ore`, `deepslate_tin_ore`, их предметы,
модели, добыча с Silk Touch/Fortune при заданном `drop`, теги `c:ores` и генерация.
`drop` — зарегистрированный предмет; без него руда выпадает сама. Пример выше использует
ванильное железо только как пример, замените своим предметом. Выбор биомов: `overworld`, `nether`, `end`.
В обычном мире руда заменяет `minecraft:stone_ore_replaceables` и `minecraft:deepslate_ore_replaceables`;
в Nether основа выбирает `minecraft:base_stone_nether`, в End — `minecraft:end_stone`.
Поля `stone_replaceables` и `deepslate_replaceables` позволяют задать свои block tags пород.
Новые руды появляются только в новых чанках.
Высоты распределяются равномерно, `veins_per_chunk` — число попыток, не гарантированное число жил.

### Механизмы

Добавьте запись в `machines`. Поля обычного блока плюс `assembled_texture` или `assembled_model`.
Каждый механизм имеет BlockEntity, сохранение `progress`, серверный обработчик, свойства `facing` и `assembled`.
Одиночный механизм считается собранным сразу. Для своей логики используйте:

```java
Machines.register("crusher", BlockBehaviour.Properties.of().strength(4),
    new MachineDefinition(null, 20, (level, machine) -> {
        machine.progress(machine.progress() + 1);
    }));
```

Не регистрируйте одно имя одновременно из Java и каталога. Демонстрационные механизмы пока только
увеличивают progress раз в секунду; инвентари, энергия, GUI и производственные рецепты будут следующим слоем.

### Мультиблоки

В `multiblocks` задайте имя и список `parts`: координаты `x/y/z` и `block`.
`block` принимает ID блока, `#namespace:tag` либо `minecraft:air` для обязательной пустоты.
Неуказанные позиции игнорируются. `(0,0,0)` зарезервирована под контроллер.
Координаты описывают структуру относительно контроллера, смотрящего на север.
Проверка автоматически поддерживает все четыре горизонтальных поворота.

В записи контроллера в `machines` укажите `"multiblock":"tech_mod:имя_структуры"`.
Когда все части на месте, сервер выставляет `assembled=true`, клиент получает новое состояние
и меняет модель контроллера. При поломке или выгрузке части обработка останавливается на следующем тике.
Проверка не загружает чанки принудительно. Части других структур не захватываются эксклюзивно;
общие корпуса допускаются. Лимиты основы: 4096 проверяемых позиций и смещение до 32 блоков по каждой оси.

Для своей модели укажите `assembled_model`, например `"tech_mod:block/reactor_assembled"`,
и добавьте соответствующий JSON в `assets/tech_mod/models/block/`. Меняется модель контроллера;
автоматического скрытия/замены остальных блоков и отдельного рендера огромной конструкции пока нет.

Тестовый мультиблок: один слой 3×3, вид сверху; контроллер смотрит на север:

```text
север
К X К   X — test_controller; К — machine_casing
К . К   . — обязательный воздух
К К К
юг
```

### JEI

Опциональная интеграция с JEI 31.17.0.94 для 26.3. Без JEI мод работает.
Для разработки: `gradlew.bat runClient -PwithJei` (JEI и MezzConfig добавляются в runtime).
В установленной игре используйте официальную сборку JEI для 26.3 и её зависимости.
Категория «Мультиблочные структуры» показывает послойные схемы, предмет контроллера и варианты блоков по тегам.
Большие слои делятся на страницы 7×7. Схема ориентирована на север, X вправо, Z вниз;
Y и начальные X/Z указаны над схемой. Пустая рамка — обязательный воздух, отсутствие рамки — позиция не проверяется.
Это инструкция сборки, автоматической постройки или переноса предметов в мир нет.

### Теги

`ModTags.block("namespace:name")`, `.item(...)`, `.fluid(...)` создают TagKey;
`ModTags.of(Registries.ENTITY_TYPE, "namespace:name")` — для произвольного реестра.
Членство задаётся данными. `tags` у блоков/механизмов/руд добавляет одновременно block и item tags;
у жидкостей добавляет источник и течение в fluid tags.
Для произвольного тега добавьте запись в верхний массив `tags` каталога:

```json
{"registry":"block", "id":"tech_mod:heat_resistant", "values":["minecraft:obsidian", "#tech_mod:machine_casings"]}
```

Можно также писать обычные datapack-файлы `data/<namespace>/tags/<registry>/<path>.json`.
В 26.3 имена каталогов реестров в единственном числе: `block`, `item`, `fluid`.

### Жидкости

```json
{"name":"brine", "display":"Brine", "display_ru":"Рассол", "color":"88CCDD",
 "tick_delay":10, "infinite":false, "tags":["tech_mod:coolants"]}
```

Добавьте в `fluids`: получите источник, течение `flowing_brine`, жидкий блок и `brine_bucket`.
Основа использует поведение воды, её анимацию, звуки, тушение и тег `minecraft:water`;
цвет жидкости задаётся `color`. `infinite` управляет превращением течения в источник.
`bucket_texture` опционально меняет текстуру ведра; по умолчанию используется ванильное ведро воды.
Из Java: `ModFluids.register(name, rgb, tickDelay, infinite)`.
Для кислоты, лавы и иных физических свойств расширяйте ModFluid/регистратор отдельным поведением.

## Зоны

`ZoneData.get(serverLevel)` хранит зоны конкретного измерения в SavedData мира.
Зоны переживают сохранение/загрузку, сохраняют позицию, размер, скорости, интенсивность и время удаления.
Сервер управляет эффектами; сетевую доставку звуков, частиц, статусов и постэффектов выполняет Minecraft.
Обработчики этой основы применяются к живым игрокам внутри зоны; наблюдатели исключены.
Изменение биомов, блоков и поведение мобов подключаются отдельной логикой через контекст эффекта.

```java
ZoneType.register(ModBlocks.id("radiation"), new ZoneType(
    List.of(ZoneEffects.status(MobEffects.POISON, 0),
            ZoneEffects.particles(ParticleTypes.SMOKE, 3, 10),
            context -> { /* context.zone().intensity(), context.level(), context.player() */ }),
    List.of(Identifier.fromNamespaceAndPath("tech_mod", "radiation"))));

Zone zone = Zone.sphere(ModBlocks.id("radiation"), new Vec3(0, 64, 0), 20)
    .moving(new Vec3(0.01, 0, 0))
    .growing(new Vec3(0.005, 0.005, 0.005))
    .until(level.getGameTime() + 20 * 60);
ZoneData.get(level).put(zone);
// Для обновления положите новую Zone с тем же id; для удаления — remove(zone.id()).
```

Скорости указаны в блоках за тик. `Zone.box(type, center, halfSize)` создаёт прямоугольную зону,
`ELLIPSOID` позволяет эллипсоид. Размеры — положительные полуоси. При сжатии до нуля зона удаляется.
`until` — абсолютный gameTime этого измерения; без него зона бессрочная. Часы идут только пока работает мир.
Обновления выполняйте на серверном потоке. `ZoneType.Effect` также предоставляет `enter` и `exit`.
Интенсивность доступна каждому обработчику; нулевая интенсивность отключает эффекты, а её интерпретация
задаётся самим обработчиком. При пересечении зон работают все их обработчики.

ID постэффекта соответствует `assets/<namespace>/post_effect/<name>.json` и его shader-ресурсам.
Для примера заражение использует ванильный `minecraft:creeper`. Поддерживаются несколько постэффектов,
общий эффект пересекающихся зон снимается после выхода из всех таких зон. При выходе снимаются только
эффекты, добавленные системой зон; сведения о них сохраняются у игрока для корректной очистки после входа.
Статусы обновляются на 40 тиков и после выхода естественно истекают, чужие зелья не очищаются.
Звуки проигрываются периодически, частицы ограничены бюджетом; это основа, без бесшовных звуковых петель.

Команды требуют прав gamemaster (уровень 2):

```text
/techzone create tech_mod:infection 10
/techzone create tech_mod:freezing 15 60 0.5
/techzone create tech_mod:warming 8 30
/techzone list
/techzone remove <id>
/techzone clear
```

Позиция создания — позиция исполнителя. Аргументы: тип, радиус, необязательный срок в секундах,
необязательный рост радиуса в блоках в секунду. `list/remove/clear` работают в текущем измерении.
Демонстрации: infection — яд, споры, звук и зелёная постобработка; freezing — замедление и снежинки;
warming — дым и поджигание. Это примеры обработчиков, ещё не симуляция температуры/заражения.

## Проверки

`gradlew.bat build` компилирует мод, генерирует данные и запускает серверные GameTests
в отдельном мире под `build/run/gameTest`. Тестовый мод в основной JAR не включается.
`gradlew.bat runClientGameTest -PwithJei` проверяет клиент в отдельном мире, делает скриншоты
и закрывает игру. Тест использует внутренний ввод Minecraft, системные мышь и клавиатура не нужны.
Клиентский тест и генерация ассетов при первом запуске требуют дополнительной загрузки.
